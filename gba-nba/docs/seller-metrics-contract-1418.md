The dashboard stock query reads only existing local Debt/ClientInDebt records, including still-unpaid older obligations/opening records. It does not fetch historical records from 1C, change the 2025 sync boundary, copy data, backfill or start workers. Since 2026-11-13 the client overdue column and debt follow-up tasks read the same documents under the same rule: the former 365-day cap, the document-date rate and the zero-day default for missing terms are gone.

Financial cache values have hard maximum ages: debt ten minutes, team ninety seconds. On expiration a refresh is required; failure propagates and the UI clears old values instead of presenting an indefinitely stale snapshot as current. The source-status component still explicitly says the latest sale activity is not proof of completed synchronization.

Read-only DEV evidence on 2026-10-22:

- 1,697 active positive debts with distinct DebtIDs; 1,696 attached to sales and one resale; none missing agreements; 1,601 have positive terms.
- Current persisted EUR payment values are populated: 33,723 UAH payments total 360,767,115.58 UAH / 7,277,439.1185 EUR, none equal the nonzero local amount and none missing EUR. USD40 and EUR268 are also populated. The old comment claiming EuroAmount contains UAH is obsolete; current sync applies document conversion in ApplyIncomePaymentCurrencyValues.
- For the active assigned-client scope, 27,731 payments total €6,041,298.5024 persisted versus €6,042,053.8600 after legacy revaluation. Existing current unpaid documents have no deleted/missing sale attachments; 296 are unassigned and intentionally outside manager dashboards.
- Final provenance-aware document snapshot query: 246 ms; legacy actionable-client aggregation: 1,054 ms. Final known overdue subtotal €62,516.00; separate unknown-date stock €59,853.79 across 129 documents and five managers. The assigned stock contains 1,401 documents; all have historical FX. These are intentionally different scopes, not equivalent-query benchmark totals.
- Of 1,690 imported positive debts across all clients, 1,530 exactly match their source-line UTC timestamp and 160 lack source lineage. `OutcomeOrdersSyncRepository.ImportedSaleBatchLineage.Source.GetImportedSaleDestinationDate` explicitly converts the normalized source date to UTC. Native `DebtRepository.Add` uses the database UTC default. An import flag by itself does not establish the clock basis.
- Actual SQL Server disposable fixture verified: current-only and future-only FX both yield unknown EUR; historical FX converts correctly; native and source-matched dates are recognized; unmatched imported dates stay in their own coverage bucket. The fixture database was removed and no DEV/QA business rows changed.
